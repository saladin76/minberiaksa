# Recurring notification cadence and campaign operations

Built on production source 5f47d434049018a13c2657fb0d9b9358bae559b4. Production inspection reproduced a monthly-only subscription signup WhatsApp message, unavailable campaign counter reads, unavailable financial attribution and a failed blocked-campaign diagnostic. No new collection, refund or live recipient message was initiated.

## Changes

- A notification loads the exact subscription linked to its focused donation, or an explicitly supplied subscription ID whose ownership is checked. Daily, every-Friday and monthly frequency labels are available in all 19 supported languages. Legacy null frequency explicitly means monthly; invalid frequency is unresolved. General donor history does not infer a subscription from the donor's latest plan.
- Email/SMS subscription notifications adapt legacy monthly wording to the actual frequency, including email subject and HTML content. Links, attributes, variable tokens and stored amounts are preserved. Renewal summaries include their actual period.
- WhatsApp signup templates receive a content-addressed, neutral recurring successor with one approved frequency parameter. Headers and button labels use neutral wording; their URLs remain intact. Sources remain immutable. Every exact language/schema must be approved on the unique active default WABA before the trigger switches. The existing approval-sync cron completes activation after approval. Until then, incompatible monthly WhatsApp notices for nonmonthly subscriptions are archived as skipped with `RECURRING_TEMPLATE_CADENCE_MISMATCH`; a wrong monthly notice is never sent. Ordinary donation receipts are independent. No historical notification replay is scheduled.
- Campaign operators use one visible Send now action for draft/review/approved campaigns. Opening the recipient preview performs no confirmation or send. The same authorized operator's final confirmation runs the existing self-confirm transition and send endpoint. Second-person approval was already removed in the deployed backend and remains removed. Coverage, permission, consent, execution leases and recipient deduplication remain enforced. Unavailable preview data no longer opens a fictitious zero-recipient send dialog.
- Delivery list loading, delivery counters and financial attribution are independent. Revenue is requested only when its view is opened. Counter snapshots run in the background and coalesce polling; a changed campaign revision starts fresh work. An unavailable read stays unavailable rather than becoming zero. Delivery and saved-list language aggregation failures have paged, read-only fallbacks with the same evidence/recipient policy; any failed page rejects the whole result. This supplies a recovery path without asserting an unverified database root cause.
- Delivery tables omit financial columns, mobile screens use compact cards, controls move into the row menu and cancelled campaigns are excluded from the active filter. Blocked-language previews open diagnosis; they do not bypass missing translations or resume campaigns automatically.
- Two additive, nonunique lookup indexes support campaign delivery and audience membership paging. No schema migration, index deletion, credential change or payment-routing change is required.

## Validation and rollout

Synthetic tests cover 19 languages × 3 frequencies, exact subscription ownership, actual channel renderers, immutable Meta sources and all-language approval activation, fallback pagination and failures, independent authenticated polling, counter revision changes and the existing single-operator permission rules. Dedicated browser fixtures cover AR/EN/TR at 390/1440 pixels, send preview/cancel/final confirmation, deletion, coverage recovery and delivery/revenue separation. They make no production writes or real provider sends.

Deploy only the pinned full commit after release gates pass, using the existing VPS release runner with `--publish --activate-approved`. Those flags submit provider template metadata and activate only fully approved families; a successful runtime deployment does not imply that Meta has approved the new family. Inspect the metadata phase and the next template-sync cron result. Do not bulk-resume or retry old campaigns as a deployment side effect. Runtime campaign readiness and actual provider acceptance require observation after deployment.
