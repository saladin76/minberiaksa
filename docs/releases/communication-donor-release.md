# Communication and donor administration release

This candidate extends the combined changes in PRs #106–#109. It does not deploy the VPS or perform live payment, campaign, or donor-message operations.

## Resulting behavior

- The existing donor administration page edits donor profile fields. ADMIN may change the email identity; STAFF with the donors permission may edit the remaining supported fields. Roles, credentials, balances, donations, and subscription references are excluded from this endpoint. Contact routing, profile updates, and the field-name audit record are transactional. A stale form receives a conflict instead of overwriting a newer update. Changing an email clears its verification flag.
- Member markers use registration credentials, a linked authentication account, or explicit `registeredAt` evidence from verified Google One Tap sign-in. The optional Mongo field is absent on legacy records and needs no data backfill. Checkout activity (`verifiedAt`) alone yields a guest marker. Records with neither registration evidence nor recorded activity remain unknown. Historical verified-email-only identities also remain unknown because email verification alone cannot distinguish One Tap from a guest verification flow. The marker appears beside donor names in administration, revenue, and WhatsApp conversation headers. Registration later upgrades the marker automatically. The administration list supports status filtering and phone search.
- Signed Meta `smb_message_echoes` events are archived as outbound Business app messages with unique provider-event keys. They participate in conversation history and pending-reply resolution, retain media descriptors, and never open a customer-service reply window or process STOP as an incoming donor request. Provider timestamps preserve ordering when webhook delivery is delayed. Archive failures request redelivery. Echo records already linked to an API delivery are not counted or displayed twice.
- Routing reads fail closed when storage is unavailable. Explicit destinations must respect channel, enabled/status/health, and declared recipient capabilities. Ties are deterministic. The same router powers execution and simulation; simulation explains matching conditions and unavailable primary/fallback destinations. SMS campaigns respect a routing refusal rather than falling back to an environment sender. Campaign delivery archives preserve the selected rule and fallback evidence.
- The WhatsApp header button reserves room for the count, has keyboard focus and an accessible count label, and avoids repeated animated notifications. Header controls wrap on narrow screens, and donor profile actions remain visible while the fields scroll. The shell refreshes the count after inbox updates, on focus, and periodically. A transient error preserves the last confirmed count. The home indicators expose refresh progress and update feedback.
- An incorrect PayPal return token cannot mutate the donation or reveal an existing success access token. A historical order lookup returning 404 remains unresolved; it is no longer automatically labelled expired/unapproved. Neither behavior initiates a new capture. Valid return capture and amount/currency settlement checks retain their existing implementation.
- Unused foreign-organization presentation code and obsolete multi-brand selectors are removed. The legacy encryption domain string remains intentionally unchanged because renaming it would prevent decrypting existing integration settings.

## Verification

Regression coverage uses synthetic data and mocked provider boundaries for echo retries, persistence failures, routing capability/fallback and storage failures, donor registration evidence, profile validation/authorization, optimistic conflicts, and PayPal mismatch/404 behavior. The browser fixture uses the real editor and header components in Arabic, English, and Turkish at desktop and mobile widths. It exercises cancel, stale-write recovery, save payloads, badges, and inbox navigation. Existing content-editor, checkout, communication, translation, and release gates remain required before merge.

Local validation passed 1,018 integration tests and 119 content-editor tests, the whole-repository TypeScript check, the communication runtime typecheck, the ESLint ratchet, and dashboard/public locale audits. The browser fixture bundle compiles. GitHub CI runs the browser fixtures and exports screenshots; a successful final run and visual review are required before merge. Header controls are checked for overlapping hit targets with both inbox buttons visible at desktop, 390-pixel and 320-pixel widths. The profile save action is checked against the viewport while the form fields scroll. The pull request records the final CI results. Credentialed production journeys remain separate from these synthetic fixtures.

## Operational acceptance still required

Albaraka's live rejection codes `59`, `0148`, and `05` cannot be cleared by a UI or code-only test. Bank tracing must establish the reason and terminal authorization for subsequent Mail Order/Recurring payments without CVC. No payload flags, recurring schedules, 2D/3D choices, or financial histories are rewritten by this candidate. A successful recurring installment is still unverified.

Live PayPal settlement must be checked against the correct merchant/environment and matching order/capture references. Seven previous 404 lookups do not prove declined payments or missing settled revenue. This release preserves uncertainty rather than converting it into a fabricated financial result.

WhatsApp Business app synchronization requires the number to be onboarded for Meta Coexistence and the app to receive the `smb_message_echoes` subscription. Ordinary standalone Business app numbers are not made Cloud API numbers by this change. Existing app chat history, edit/revoke echoes, and contact-history import are outside the new-message ingestion path. No re-onboarding, subscription mutation, history import, or real message is attempted automatically. After grouped deployment, verify an app-originated reply on a known onboarded number appears once and closes only the correct pending conversation.

Google Ads and Search Console require their appropriate read permissions; saved fields do not prove access. Previously supplied Google Ads conversion settings still require an explicit production save. Provider-backed editorial generation and delivered notification totals require a post-deployment check. Browser fixtures establish application behavior, not provider acceptance.
